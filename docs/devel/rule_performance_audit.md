## Goal command

Paste this command into Codex when the audit needs to be rerun after rules are added, removed, renamed, or modified:

```text
/goal Audit every pydocformatter rule category and rule implementation for unnecessarily or avoidably slow code. First update every inventory table in docs/devel/rule_performance_audit.md from the latest Git-tracked rule category and rule implementation files, because rules may have been added, removed, renamed, or substantially changed since the rule inventory up-to-date commit recorded at the top of the file. Then measure or otherwise characterize performance, analyze the implementation code for behavior-preserving speedups, and maintain docs/devel/rule_performance_audit.md continuously as the source of truth. Do not implement fixes during the audit unless I explicitly ask for an implementation pass. Do not recommend externally visible behavior changes unless they are confirmed bugs; if an apparent speedup depends on changing behavior, record the bug-versus-intended-behavior question in the plan and ask me to confirm before treating it as an optimization. The goal is complete only when every category and every rule row in the plan has performance evidence, code-analysis notes, potential speedup classification, and any detailed findings or no-finding rationale recorded.
```

## Status legend

- `Not started`: no audit work recorded yet.
- `Measuring`: timing or profiling is underway.
- `Analyzing`: implementation code is being inspected.
- `Done`: performance evidence and code-analysis notes are recorded.
- `Blocked`: progress needs user input or missing tooling.

Potential classifications:

- `None`: no behavior-preserving speedup identified beyond normal shared framework costs.
- `Low`: possible cleanup with narrow or workload-dependent benefit.
- `Moderate`: likely measurable on realistic larger workloads or when several affected rules are selected.
- `High`: clear avoidable pathological cost with direct measurement.

### Finding 1: PDF101 variable-width source wrapping has quadratic long-paragraph cost

- **Status:** Fixed
- **Potential:** High
- **Affected rows:** `PDF101`; indirectly any run selecting docstring reflow.
- **Files/functions:** `src/pydocformatter/rules/definitions/PDF/PDF101_docstring_reflow.py`; `src/pydocformatter/rules/definition_helpers/string_literals.py::_wrap_source_words_with_variable_widths`; `src/pydocformatter/rules/definition_helpers/text_layout.py::advance_display_column`
- **Evidence:** Audit benchmark with `PDF101` selected, `url_aware_wrapping=False`, and one single-line summary: 100 words 0.014s mean, 300 words 0.269s, 600 words 1.941s, 1000 words 8.453s. Before implementation in the current workspace through `format_source`: 100 words 0.057218s, 300 words 1.077019s, 600 words 7.783112s, 1000 words 34.268487s. After implementation through the same `format_source` benchmark: 100 words 0.003641s, 300 words 0.008028s, 600 words 0.011594s, 1000 words 0.022954s.
- **Code analysis:** `PDF101` passes variable `initial_width`, `subsequent_width`, and `final_suffix_width` to `wrap_source_words()`. Without URL-aware wrapping, that dispatches to `_wrap_source_words_with_variable_widths()`. The previous cached `best(start, first_line)` tried every candidate end position from the suffix for each start, preserving a minimum-line-count layout but creating avoidable quadratic cost for long prose.
- **Implemented fix:** Replaced the recursive minimum-line-count search with greedy longest-fitting-line wrapping. This preserves the current scoring policy because the previous chooser minimized line count and iterated longest current-line candidates first on ties.
- **Behavior-risk analysis:** Low after implementation. A targeted non-mutating comparison over 58,300 generated variable-width wrapping cases matched the previous implementation, and focused helper tests now cover initial/subsequent width differences, final suffix width, long unsplittable words, and tab-expanded source widths.
- **Tests/verification:** `uv run pytest tests/rules/definition_helpers/test_string_literals.py tests/rules/PDF/test_PDF101.py` passed with 64 tests.
- **User decisions needed:** None. Any future optimization that intentionally changes wrapping output should still be treated as a behavior question first.
