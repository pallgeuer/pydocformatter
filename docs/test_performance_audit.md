## Status Legend

- `Not started`: no audit work recorded yet.
- `Measuring`: timing or profiling is underway.
- `Analyzing`: test, fixture, or helper code is being inspected.
- `Done`: performance evidence and code-analysis notes are recorded.
- `Blocked`: progress needs user input or missing tooling.

## Potential Legend

- `None`: no credible coverage-preserving speedup found.
- `Low`: small or uncertain speedup, likely not worth immediate implementation.
- `Medium`: localized coverage-preserving speedup with measurable value.
- `High`: repeated or suite-wide cost with clear coverage-preserving mitigation.
- `Test-design decision`: possible speedup would alter coverage, assertion strength, fixture realism, or test semantics and needs explicit user approval.

## Findings

### Finding 1: Rule Markdown example tests repeat formatter work across three passes

- **Status:** Open
- **Potential:** Medium
- **Affected rows:** `tests/test_rule_markdown_examples.py`; Rule Markdown example execution; Repeated settings and rule collection setup.
- **Files/functions:** `tests/test_rule_markdown_examples.py::test_rule_markdown_examples_match_rule_implementation`; `tests/test_rule_markdown_examples.py::test_rule_markdown_clean_examples_have_no_hidden_fix_changes`; `tests/test_rule_markdown_examples.py::test_rule_markdown_examples_account_for_initial_check_findings_after_fixing`
- **Evidence:** Per-file aggregation reports `tests/test_rule_markdown_examples.py` as the dominant file at `2.113s` aggregate and `2.056s` call time; focused run passed `152` items in `2.37s`. The cost split over 48 rules and 361 examples measured Markdown load `0.0009s`, example parsing `0.0054s`, settings plus selection once per example `0.0553s`, one fix pass per example `0.5529s`, one check pass per example `0.2487s`, and one direct rule fix pass per example `0.5551s`.
- **Code analysis:** The three rule-parametrized tests each load and parse the same rule Markdown, build settings/selections for the same examples, and run overlapping formatter/check/fix paths. Parsing is not the bottleneck; repeated formatter execution is. The second and third tests both begin with a check pass for every example, and the first and third tests both run fix-like paths for every example.
- **Coverage-preserving approach:** In a future implementation pass, build a per-rule helper that loads/parses examples once, validates example settings once, builds settings/selection once per example, runs the initial check once, and then performs the existing output, hidden-fix, and finding-correspondence assertions from shared results where equivalent. Preserve per-rule parametrization and assertion messages so failures still identify the rule and example.
- **Coverage-risk analysis:** Low if all existing assertions remain and the cached result is scoped to one test invocation or immutable example data. Do not skip direct `_run_fix_pass()` hidden-clean checks or the `run_rules(..., fix=True)` correspondence check; only share setup/check results that are exactly identical to current calls.
- **Tests/verification:** After any implementation pass, run `uv run pytest tests/test_rule_markdown_examples.py --durations=20 --durations-min=0.001 -q` and the full `uv run pytest --durations=0 --durations-min=0.001 -q`; both commands use project-default pytest-xdist multiprocessing unless `-n 0` is passed.
- **User decisions needed:** None for a coverage-preserving implementation pass.
